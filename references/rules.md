# 规则依据

这份文件说明每条规则为什么存在、什么时候可以例外、出自哪里。SKILL.md 只写怎么做，这里写为什么。

## 总体来源

中文没有官方的受控语言标准，没有和 ASD-STE100 对等的东西。本 skill 的规则来自以下几处：

| 来源 | 用到的内容 |
|---|---|
| ASD-STE100 Issue 9（2025） | 总体思路：一词一义、主动语态、一句一个指令、短句、不省略、不用分号。本项目不复制它的词典和条文。 |
| GB/T 1.1-2020《标准化工作导则 第 1 部分》附录 C | 能愿动词按要求、推荐、允许、能力、可能性分组，组内用词固定，不互换。这里只转述，不复制条文。 |
| 《民法典》第一千二百五十九条 | 法律上「以上、以下、以内」包括本数，「不满、超过、以外」不包括本数。日常读者和模型不一定按这个理解，所以本 skill 要求写明。 |
| GB/T 15834-2011《标点符号用法》 | 分号和破折号的用法。本 skill 比国标更严，不用分号。 |
| RFC 2119 | 英文 MUST / SHOULD / MAY 和中文情态阶梯的对应关系，方便中英双语的工具描述保持强度一致。 |
| 余光中《怎样改进英式中文》 | 形式动词（「进行」「作出」）、「的」字链、名词化、滥用被动。 |
| 阮一峰《中文技术文档的写作规范》 | 句长、标点、中英混排。 |

参考过的开源项目（只借鉴思路，没有复制文字）：

- [danyuchn/asd-ste100-skill](https://github.com/danyuchn/asd-ste100-skill)：严格 / 风格两种模式、结构类和词汇类规则分开、默认只输出改写结果、`Kept as-is` 附加行、linter 不要求删除推测语气。
- [heichaowo/jianming-zhongwen](https://github.com/heichaowo/jianming-zhongwen)：情态阶梯用「必须 / 不得」而不用「应」，句长上限的校准，形式动词只在后接动名词时才算命中。
- [bjo4/controlled-technical-chinese](https://github.com/bjo4/controlled-technical-chinese)：用「两个读者会不会做出不同动作」判断严重程度，区分真歧义和刻意模糊（「请稍后再试」）。

## 结构类规则

### 写明执行者

中文可以省略主语，英文不行。人读「检查配置后重启」时，会用常识补出主语。agent 没有这种常识。如果一句里有两个动作，而执行者可能不同（调用方传参数，工具返回结果），每个动作都要写明执行者。

**例外：**编号步骤里的祈使句。读者就是执行者，可以不写主语。

**linter 不查：**判断是否省略需要理解句子，正则做不到。

### 一句一个动作、句长

句长上限：步骤 30 字，描述 50 字，逗号分句 40 字。这些数字和 jianming-zhongwen 的校准结果一致，也在 STE 的 20 / 25 词按常见中英换算后的区间内。它们是诊断信号，不是目的。句子有两个动作时，即使只有 20 字也要拆。

字数计法：每个汉字计 1，每个英文单词或数字计 1，每个行内代码计 1，标点不计。

### 「的」字链不超过 2 层

「服务器端的连接池的超时时间的默认值」有 3 个「的」，读者要回头才能分清修饰关系。改法：去掉不必要的「的」（「连接池超时的默认值」），或者拆成主谓句（「连接池的超时有一个默认值，是 30 秒」）。

linter 只数结构助词「的」，不计「目的」「的确」「的话」「有的」「真的」。

### 形式动词

「进行 / 作出 / 予以 / 加以 / 开展 / 实施 / 给予 / 执行」后接动名词时，真正的动作藏在名词里。直接用动词。

「进行中」「执行文件」这类用法不算：linter 只在后面跟着动名词，或者是「进行……操作」时才报告。

### 边界含不含本数

法律上「3 次以上」包含 3 次。但很多人读成「多于 3 次」，模型的理解也不稳定。只要边界会影响动作（报警阈值、重试次数、保留天数），就改成没有歧义的写法：

| 原文 | 改写 |
|---|---|
| 3 次以上 | ≥ 3 次 / 不少于 3 次 / 3 次或更多 |
| 3 次以下 | ≤ 3 次 / 不超过 3 次 |
| 超过 3 次 | 保持不变，「超过」不含本数 |
| 7 天以前 | 早于 7 天前（不含第 7 天）。如果原文没说，就写明待确认 |

**严格模式**是硬违规，**风格模式**是建议。

### 否定范围

「并非所有表都支持增量同步」说的是「至少一张表不支持」，但常被读成「所有表都不支持」。写成肯定的数量（「5 张表中有 2 张不支持」），或者写成列表。

双重否定（「不得不」「不是不能」）要读者多做一次取反，改成肯定句。

linter 会排除疑问句里的「会不会不同」「是不是不」。

### 「和 / 或」混用

「A 和 B 或 C 为空时报错」有两种读法：(A 和 B) 或 C，或者 A 和 (B 或 C)。同一句里同时出现「和」和「或」，就改成列表。

linter 只报建议：很多句子虽然同时出现「和」「或」，但并没有歧义。

### 代词

句首的「它」「其」「这」「此」，在前文有两个以上名词时就有歧义。重复名词比用代词长几个字，但只有一种读法。

linter 只报建议，并且排除「这里」「此外」「其中」「其他」「该 + 名词」。

### 条件挂靠

「不建议在生产环境使用。除非迁移已完成。」第二句单独成句后，读者不知道「除非」限制的是哪个指令。条件和例外必须和它约束的动作在同一句里。

**linter 不查。**rewrite-fidelity 也查不出来，因为所有标记都还在。只能靠模型逐条核对。

### 警告的位置

警告放在它约束的那一步里，不放在段尾。agent 按顺序执行，读到段尾的警告时，动作已经做完了。

## 词汇类规则

严格模式下是硬违规，风格模式下是建议。

### 情态阶梯

| 强度 | 用词 | RFC 2119 | 不用 |
|---|---|---|---|
| 要求 | 必须 / 不得 | MUST / MUST NOT | 应该、应当、务必、需要（表示要求时） |
| 推荐 | 建议 / 不建议 | SHOULD / SHOULD NOT | 最好、尽量、宜 |
| 允许 | 可以 / 不必 | MAY / NEED NOT | 可（单字） |
| 能力 | 能 / 不能 | CAN / CANNOT | |
| 可能性 | 可能 / 不可能 | — | 也许、或许、大概、似乎 |

GB/T 1.1 的要求级用「应 / 不应」，并且有意不用「必须」。原因是标准文件需要把自身的要求和法律等外部约束分开。工具描述和提示词没有这个需要，而普通读者常把「应」读成弱建议。所以本 skill 默认用「必须 / 不得」。文本本身是标准文件时，改用 GB/T 1.1 的写法。

**推荐级需要默认动作。**一致率评测（[`evals/agreement`](../evals/agreement/README.md)）里有一个反例：「最好不要覆盖文件，除非用户设置了 force」被读成「默认不覆盖」的有 7 / 9。改写成「不建议覆盖，除非用户设置了 force」后，只有 1 / 9 这样读，3 / 9 读成「由工具决定」，5 / 9 判断不了。「建议」只表达倾向，不规定行为。写工具描述时，推荐级后面应该跟一句默认动作，例如「默认不覆盖」。

**只替换，不删除。**原文强度不明确时（「应该」可能是必须，也可能是建议），保留原词，交给作者决定。

### 一词一义

同一个概念全文只用一个词。linter 内置了几组常被轮换的词（删除 / 移除 / 清除，配置 / 设置，修改 / 更改 / 变更……）。如果它们在你的领域里是不同的概念，用 `--disable synonym-rotation` 关闭这条规则，或者在项目术语表里写明区别。

### 模糊词

「定期」「大量」「尽快」「适当」「较大」无法判定是否满足。能改成可判定的条件就改。系统确实不知道具体值时（「请稍后再试」），可以保留。

## 明确不做的事

- **不查「了」的时态歧义。**需要上下文。SKILL.md 里有改写指引。
- **不查中英文之间的空格和全角半角。**这是排版问题，用 [autocorrect](https://github.com/huacnlee/autocorrect) 处理。
- **不分词。**linter 只用标准库正则，零依赖，启动快，可以放进 hook。代价是对单字词（应、能、被）要靠排除表，会有少量误报。
- **不做繁体中文。**繁体的用词和地区习惯不同，推荐 controlled-technical-chinese。
